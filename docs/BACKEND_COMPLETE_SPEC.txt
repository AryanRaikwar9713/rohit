4) LONG VIDEO (CHANNEL) – UPLOAD, LIST, EDIT, DELETE (YOUTUBE-STYLE)
--------------------------------------------------------------------------------
After a user has created a video channel (existing channel_api create_channel),
they must be able to upload long/full videos and manage them (view, edit, update, delete).

A) Upload long video
   - Endpoint: e.g. POST long_video_api.php?action=upload (or your convention)
   - Auth: logged-in user, must have a channel.
   - Input: multipart/form or similar
     - title (string, required)
     - description (string, optional)
     - video file (required)
     - thumbnail (optional)
     - channel_id or infer from logged-in user’s channel
   - Response: video id, title, url (or stream URL), thumbnail, created_at, etc.

B) List my long videos
   - Endpoint: e.g. GET/POST long_video_api.php?action=list_my_videos
   - Auth: logged-in user
   - Returns: list of videos belonging to the user’s channel
     - id, title, description, video_url (or stream key), thumbnail_url,
       duration (optional), created_at, updated_at, status (optional)

C) Get one long video (for edit screen / playback)
   - Endpoint: e.g. long_video_api.php?action=get_video&video_id=<id>
   - Auth: only owner (or public if you want public long videos).
   - Returns: same fields as one item in list.

D) Update long video
   - Endpoint: e.g. POST long_video_api.php?action=update
   - Auth: only owner
   - Input: video_id (required), title, description, optionally new thumbnail.
     Video file replace is optional (if you support re-upload).
   - Response: success + updated video object.

E) Delete long video
   - Endpoint: e.g. POST long_video_api.php?action=delete
   - Auth: only owner
   - Input: video_id
   - Response: success.

F) List public long videos (for Long/Home page – show all users’ uploads)
   - Endpoint: POST long_video_api.php?action=list_public
   - Auth: optional (logged-in or anonymous)
   - Input (query): page (int, 1-based), limit (int, e.g. 10). Flutter calls: ?action=list_public&page=1&limit=10, then page=2 for "Load more".
   - Returns: JSON
     { "videos": [ { "id", "title", "description", "video_url", "thumbnail_url", "duration", "status", "created_at", "updated_at", "like_count", "comment_count" }, ... ],
       "has_more": true|false }
   - Only return videos that are public/approved (e.g. status = 1 or your convention). New uploads must appear here so users see them on the Long page.
   - has_more: true if there are more pages (e.g. total > page * limit).
   - Flutter uses this on the Long (Home) page in the "User uploads" section with pagination; everyone can see and play uploaded videos.

G) Fast loading (YouTube-like) – user-uploaded long videos
   - Problem: Single large MP4 URLs load slowly (like 1G) even on 5G; users expect fast start.
   - Solution (backend): Serve long videos for streaming, not one big file.
     (1) HLS: Prefer converting uploads to HLS (e.g. .m3u8 + .ts segments). Return video_url
         pointing to the .m3u8 playlist. Flutter detects .m3u8 and uses HLS mode for fast,
         segment-by-segment loading (first chunk loads quickly, playback starts early).
     (2) CDN: Serve video (HLS or MP4) from a CDN so users get low latency and range requests.
     (3) Range requests: If you keep single MP4, ensure the server supports HTTP Range
         (Accept-Ranges: bytes) so the player can request only the beginning of the file
         for fast start.
   - Flutter: If video_url contains ".m3u8", the app treats it as HLS automatically. No
     extra app change needed once backend returns HLS URLs.

Flutter will:
- In drawer under “Long”/Clips section, show “My long videos” (and/or “Upload long video”)
  when user has a channel.
- Screen to list user’s long videos, open to play or edit, and options to edit/delete.
- Upload screen for new long video after channel exists.

9) REELS – FAST DELIVERY (TIKTOK / INSTAGRAM / YT SHORTS–LIKE SPEED) (CRITICAL)
--------------------------------------------------------------------------------
Users expect reels to start in under 1–2 seconds on any network (5G, 4G, or weak). Currently
reels can feel like "1G speed" (slow start, buffering). Backend must deliver reels so that
playback starts almost instantly, like TikTok/Instagram/YouTube Shorts.

A) PROBLEM
   - Single large MP4 URLs cause slow first-byte and long buffering.
   - Users abandon after ~90 seconds of buffering; each extra second of start delay drops
     engagement. Target: no visible delay (< 2 seconds to first frame).

B) SOLUTION – BACKEND MUST DO THE FOLLOWING

   (1) CDN (mandatory)
       - Serve ALL reel video URLs (video_url in get_reels / reel feed API) from a CDN.
       - Use 200+ PoPs (or your CDN's edge nodes) so users hit the nearest edge.
       - GeoDNS or edge routing so requests go to closest server.

   (2) HLS for reels (strongly recommended)
       - Convert/transcode reels to HLS: short segments (e.g. 2–4 second .ts segments, .m3u8 playlist).
       - Return video_url pointing to the .m3u8 playlist in the reel feed API.
       - Flutter (media_kit) can play HLS; app can use same URL if .m3u8.
       - First segment is small so first frame loads in < 1–2 seconds.

   (3) If keeping single MP4 (minimum)
       - Enable HTTP Range requests (Accept-Ranges: bytes) on the CDN/origin.
       - Player can request only the first chunk (e.g. first few MB) for fast start.
       - Encode reels at moderate bitrate (e.g. 720p) so first chunk is small.

   (4) First-segment / first-chunk priority
       - Ensure the first segment (HLS) or first byte range (MP4) is cached at the edge and
         served with low latency. This is what makes "instant" start.
       - Prefer 720p (or one quality) for feed so first segment is small and fast.

   (5) Optional (for scale)
       - "Hot" reels (new or viral): keep on fast storage (e.g. SSD) and/or aggressive edge cache.
       - Multiple qualities later if needed; for now one fast quality (e.g. 720p) is enough.

C) FLUTTER APP – ALREADY DONE
   - App preloads current + next 2–3 reels and disposes distant ones.
   - If backend returns video_url as .m3u8, media_kit will play HLS.
   - No app change required once backend serves HLS or Range-enabled CDN URLs.

D) CHECKLIST FOR BACKEND
   [ ] Reel feed API (get_reels) returns video_url served from CDN (not direct origin).
   [ ] Reel video_url is either (a) HLS (.m3u8) or (b) MP4 with Accept-Ranges: bytes.
   [ ] First segment / first chunk optimized (small, cached at edge) for < 2s start.
   [ ] Optional: transcode uploads to HLS with short segments (2–4 s) for reels.
